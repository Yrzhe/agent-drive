### Added

- **Shared Spaces P1 Task 5 — space-scoped cross-owner memory reads + recall.** The memory twin of Task 4: every owner-scoped MEMORY **read** now returns the caller's own rows UNION memories reachable through their active space memberships (design §Read-path change / §Security spine #1). A new `memoryReadableFilter(db, userId)` helper (`lib/spaces.ts`) returns the Drizzle condition `owner_id = me OR memories.id ∈ accessibleMemoryIds(me)` and is applied in every memory read path: REST `GET /v1/memory` (list), `GET /v1/memory/:idOrKey` (get), `GET /v1/memory/search` (FTS recall), and the MCP equivalents `recall` / `list_memories`. A member sees a contributed memory by get + list + recall (found by its content token); a non-member sees none of it.
  - **FTS recall keeps foreign private memories out.** `recallMemories` applies the readable filter to the JOINED `memories` rows (not the FTS index): the caller's own memories + space-reachable memory ids are unioned, then ranked (`f.rank`) and limited in a single query, so a foreign private memory can never surface even when its content token matches the FTS MATCH. The `memories` table is referenced unaliased so the widened filter (built against the `memories` table object) resolves.
  - **Isolation preserved by construction.** The helper reduces to the exact pre-Spaces `eq(memories.ownerId, userId)` filter when the caller has no reachable space memories (`accessibleMemoryIds` returns `[]`), and to `undefined` (legacy trust-any) when `userId` is null — so a non-member sees the same 404/empty as full #30 isolation. The #30 `ownership-isolation` suite passes unchanged.
  - **Writes stay owner-only.** `remember` (create/update), `forget` (delete) and rebuild-index are deliberately NOT widened — a member cannot edit or delete another owner's contributed memory in P1 (role-gated space writes are Task 6). A member's `remember` with another owner's key creates a SEPARATE row under their own ownership; it never overwrites the contributor's memory.
  - Suite green: 47 unit + 285 integration (new `spaces-read-memory.integration.test.ts`, adversarial two-owner). Local-only, not deployed.

- **Shared Spaces P1 Task 4 — space-scoped cross-owner file reads + download.** Every owner-scoped FILE **read** now returns the caller's own rows UNION files reachable through their active space memberships (design §Read-path change / §Security spine #1). A new `fileReadableFilter(db, userId)` helper (`lib/spaces.ts`) returns the Drizzle condition `owner_id = me OR files.id ∈ accessibleFileIds(me)` and is applied in every file read path: REST `GET /v1/files` (list, incl. recursive), `GET /v1/files/search`, `GET /v1/files/:id`, `GET /v1/files/:id/preview` (download presign — a space file signs the CONTRIBUTOR's `s3Uri`, cross-owner, only when membership matched it), and the MCP equivalents `list_files` / `read_file` / `search_files`. A member sees a contributed file and a contributed folder's whole subtree; removing the item or the member revokes access (404/empty again).
  - **Isolation preserved by construction.** The helper reduces to the exact pre-Spaces `eq(files.ownerId, userId)` filter when the caller has no reachable space files (`accessibleFileIds` returns `[]`), and to `undefined` (legacy trust-any) when `userId` is null — so a non-member sees the same 404/empty as full #30 isolation. Both #30 suites (`ownership-isolation`, `ownership-collision`) pass unchanged.
  - **Writes stay owner-only.** Rename/move/delete/restore/purge/overwrite and share/send are deliberately NOT widened — a member cannot mutate another owner's space file through these paths in P1 (role-gated space writes are Task 6).
  - Suite green: 47 unit + 276 integration (new `spaces-read-files.integration.test.ts`, adversarial two-owner). Local-only, not deployed.

- **Multi-tenancy Part ② Task 2 — account status + waitlist-apply endpoints (#30).** `GET /api/public/v1/account/status` → `{ status, email, isAdmin }` (calls `resolveAccessStatus`, which materializes the caller's `user_access` row on first call). `POST /api/public/v1/account/apply { message?, ref? }` attaches an optional waitlist message/referral to the caller's `pending` row; a no-op when already `active`, and it never sets `active` itself — only admin approval (a later task) does. Both are session-only (`requireSessionAuth`, 403 `session_required` for bearer callers).
  - **Deliberately exempted from the single-owner boundary.** `requireDualAuth`'s `assertRequestOwner()` call previously rejected *every* non-owner session with 403 `not_owner`, which would have made these endpoints unreachable by the very `pending`/`suspended` users they exist to serve. `/api/public/v1/account/*` is now the one path pattern skipped by that assertion — confirmed by first reproducing the 403 with the exemption reverted, then re-adding it. The forthcoming access-gate (Task 3) will need the same exemption for its own pending/suspended check.
  - `/apply`'s `message`/`ref` fields are three-way parsed (omitted vs. explicitly cleared vs. provided) so a follow-up call without a message never wipes one sent earlier; capped at 500 / 128 characters respectively (400 `validation_error` over the limit).
  - Suite green: 47 unit + 161 integration (7 new). Local-only, not deployed.

EdgeSpark exposes no app-level email-transport config — prod verification email is platform-delivered and can only be confirmed on a deployed cloud environment (a go-live checklist item). `disableSignUp` stays `true` until go-live.
  - Suite green: 47 unit + 183 integration. Local-only; auth config applied + signup flipped at go-live only.

### Security

- **Multi-tenancy Part ② re-review — gate the MCP surface by access status (#30).** The prior fix gated REST `/api/public/v1/*` but left the MCP surface (`POST /api/public/mcp`) ungated, and MCP is the product's primary agent transport. Exploit: an active non-owner mints a drive token (`POST /tokens`, session-bound to their own `user.id`, not owner-only), the admin suspends them, and the still-valid token reached full drive content (`read_file`, `write_file`, `create_share`, `send_file`) through MCP `tools/call` — REST returned `403`, MCP returned content. Fixed:
  - Extracted a shared `checkAccessGate(db, principal)` helper in `lib/access.ts` (active → `null`, pending/suspended → `{ code, message }`); `middleware/access-gate.ts` now consumes it (behavior unchanged), so every content surface shares one implementation.
  - `routes/mcp.ts` now calls `checkAccessGate` right after `authenticateMcpBearer` succeeds and before any method dispatch: a suspended/pending principal gets a JSON-RPC error (`-32000`, message carrying `access_suspended`/`access_pending`) and never reaches `callMcpTool`. The legacy global AGENT_TOKEN on an `OWNER_EMAIL`-unset deployment (`userId === null`, trust-any) passes through; the owner-bound AGENT_TOKEN resolves `active` by owner id and passes. OAuth consent is unaffected (already owner-only via `assertRequestOwner()`).
  - Defensive: `resolveAccessStatus` now resolves a bearer principal's email by id (from `es_system__auth_user`) on first materialization, so an allowlisted user whose `user_access` row is first seen via a bearer (email null) resolves `active`, not spuriously `pending`.
  - Suite green: 47 unit + 193 integration (3 new). Server-only, local-first — not deployed, `disableSignUp` stays `true`.

- **Multi-tenancy Part ② final-review hardening — gate bearers by status + owner-by-id (#30).** Three access-control findings from the whole-branch review, all rooted in owner/active identity being decided by an email string compare instead of a uniquely-resolved owner **id**, and the gate confining only sessions.
  - **[CRITICAL] Suspended user kept access via a pre-minted bearer.** `POST /tokens` mints a drive token bound to `auth.user.id` with no owner check, so an active non-owner can mint one for themselves; the access-gate then passed **every** bearer through unchecked, so the token survived the admin suspending them. `requireActiveAccess` now status-checks bearer principals too (`resolveAccessStatus` on `restAuth.ownerId`): a suspended token-holder gets `403 access_suspended`; only the legacy global AGENT_TOKEN on an `OWNER_EMAIL`-unset deployment (`ownerId === null`, trust-any) still passes without a lookup, and the owner-bound AGENT_TOKEN resolves `active` by owner id. Defense-in-depth: suspending/rejecting a user now revokes their outstanding `oauth_tokens` rows so a lingering OAuth refresh token cannot mint fresh access tokens.
  - **[MAJOR] Case-only OWNER_EMAIL duplicate self-activated + killed the admin plane.** `resolveAccessStatus` short-circuited the owner by a case-insensitive email compare; auth-user uniqueness is on the RAW email, so `Owner@x`/`owner@x` both matched and both bypassed a stored `suspended` row, while `resolveOwnerUserId` returned null on the same ambiguity and 403'd the whole admin plane. Owner is now established by `resolveOwnerUserId` id match — a duplicate falls through to its authoritative `user_access` status.
  - **[Minor] `/account/status` `isAdmin` over-reported.** It derived `isAdmin` from `isRequestOwner()` (trust-any true when `OWNER_EMAIL` unset), so the web AdminPage rendered for everyone though every admin API fails closed. Now derived from a `resolveOwnerUserId` id match, consistent with `assertAdmin`.
  - Suite green: 47 unit + 190 integration (7 new). Server-only, local-first — not deployed, `disableSignUp` stays `true`.

### Changed

- **Multi-tenancy Part ①b — per-owner constraint surgery (#30).** The destructive migration: `files.path`, `memories.key`, `contacts.name`, `contacts.url` global uniques → composite `(owner_id, X)`; `bundle_versions` gains a surrogate `id` PK with `unique(owner_id, prefix)` (`publicId` stays global). Two owners can now hold the same path/key/name/prefix; same-owner duplicates still 409. Lands the two ①a deferrals (owner-scoped memory upsert-by-key, concurrency-safe `ensureFolderChain`). Requires a fresh backfill (0 NULL owners) + a D1 snapshot before applying — see `docs/implementation/part1b-deploy-runbook.md`. Behaviour-neutral at single-owner.
  - **Migration risk differs per file, precisely:** `0016_massive_marauders.sql` (files/memories/contacts) is a clean `DROP INDEX` / `CREATE UNIQUE INDEX` swap — no table rebuild, no data movement, and `DROP INDEX` is not on EdgeSpark's destructive-operation blocklist, so it is expected to apply with a plain `edgespark db migrate` (no `--confirm-dangerous`). `0017_bundle_versions_surrogate_pk.sql` (`bundle_versions`) is a genuine table rebuild — `CREATE __new_bundle_versions` → `INSERT ... SELECT` (hand-augmented with `lower(hex(randomblob(16)))` to mint the surrogate `id`, since drizzle-kit cannot invent it for existing rows) → `DROP TABLE bundle_versions` → rename — and its `DROP TABLE` **requires** `--confirm-dangerous`.
  - **Test suite rounded out (#30 Part ①b review):** same-owner duplicate rejection now covered for memories and contacts (previously only files); keyless memories (`key: null`) proven distinct under the composite unique (NULLs don't collide); REST-layer 409 `path_conflict` proven through the route stack, not just the `isPathUniqueConflict` helper directly; and a REST-driven two-owner suite (folder create, file upload, `remember`) proves each owner reads back only their own row at an identical path/key. That last suite caught a real bug: `POST /api/public/v1/folders`'s pre-insert conflict check queried `files.path` without an `owner_id` filter, so it 409'd a second owner attempting a path the first owner already held — silently defeating the composite unique at the REST layer. Fixed in `server/src/routes/folders.ts` to match the existing owner-scoped precheck pattern already used by the upload route.

- **Multi-tenancy Part ①a — owner-scoped queries (#30).** Every owner-facing read/lookup (files, memory, shares, contacts, activity, bundles — REST + MCP) now filters by the current owner; public surfaces (`/s`, `/inbox`, `/b`) stay resolvable by resource. Behaviour-neutral at single-owner; a two-owner adversarial suite proves a bearer bound to owner B sees none of owner A's data. Same-path/key *collision* handling is Part ①b (constraint surgery). Not yet deployed.

- **Multi-tenancy Phase 2 (slice 2) — `activity_log` owner-on-insert (#30).** Completes owner-on-insert for the 7th owned table, the one deferred in slice 1 (`logEvent` has ~30 callers, which is why it waited). `ActivityEventInput` gained an `ownerId` field; `logEvent`/`logEventsBatch` stamp it. Each call site supplies the owner from the local principal: authed REST routes read `c.get("ownerId")`, public-share audit rows use the resolved `share.ownerId` (an unauthenticated download still belongs to the share's owner), inbox deliveries use `contact.ownerId`, and `softDeleteSubtree` takes an explicit `ownerId` option threaded from its route caller. No `AsyncLocalStorage` (the platform's esbuild can't bundle `node:async_hooks`) — plain explicit threading via the Hono context. New activity rows are now owned; existing rows were already backfilled. Tests assert the memory/inbox/public-share activity rows carry the right owner; mutation-verified (neutering the stamp fails all three). Suite green: 47 unit + 105 integration.

- **Multi-tenancy Phase 2 (slice 1) — owner-on-insert (#30).** Still **behaviour-neutral** at single-owner scale (nothing filters by owner yet), but closes the Phase 1a gap where new rows kept writing `NULL`: every `INSERT` into the 6 owned **content** tables (`files`, `shares`, `webhooks`, `contacts`, `memories`, `bundle_versions`) now stamps `owner_id` with the id of the principal that created the row. **Forward-correct for signup:** the owner is the *authenticated caller*, not the deployment owner, so the same code is right once a second owner exists. The owner is resolved once per request into the Hono context (`requireDualAuth` sets `c.var.ownerId` = session `auth.user.id` / bearer token `userId`); REST route handlers read it via `c.get("ownerId")`, MCP threads it as a `callMcpTool` argument (token `userId`), and inbox deliveries use the **receiving contact's `ownerId`** (a delivery belongs to whoever owns the contact, not the external peer). The three shared insert helpers (`ensureFolderChain`, `rememberMemory`, `storeInboxFile`) take an explicit `ownerId` parameter. **Insert-only, never update:** where a values object is shared between an insert and an update branch (MCP `write_file`, bundle manifest/history/version), owner is spread onto the insert path only, so an overwrite never reassigns ownership. **`activity_log` owner-on-insert is deferred** — the audit log has the worst caller fan-out (`logEvent` × 40) and its `owner_id` is naturally populated alongside the later activity-filtering work; the column already exists (migration 0015), so this is an additive follow-up. (An earlier iteration used `hono/context-storage` / `AsyncLocalStorage` to reach the deep helpers, but EdgeSpark's esbuild bundle can't resolve `node:async_hooks` and exposes no compat-flag knob — so the mechanism is explicit threading, which is also simpler to review.) Unresolved-owner requests (legacy deploy) still write `NULL` (the nullable-column policy). New Phase-2 integration suite (12 tests) drives real `app.request` flows across folders + auto-created parents, upload-init, MCP `write_file`/`create_share`, REST `POST /shares`, `remember` (incl. update-preserves-owner), bundle `/commit` (`bundle_versions` + manifest file), inbox delivery (owner = `contact.ownerId`), webhooks, and the legacy-null path; mutation-verified. Suite green: 47 unit + 104 integration. Deferred: `activity_log` owner-on-insert, Phase 1b constraint surgery (composite `(owner_id, X)` uniques + bundle-PK rebuild — the one destructive migration, converged to the last moment before signup), owner-filtered reads (only after a fresh backfill sweep confirms no `NULL`s), and the adversarial two-owner isolation suite.

- **Multi-tenancy Phase 1a — additive `owner_id` + backfill (#30).** Still **behaviour-neutral** (nothing filters by owner until Phase 2). Migration `0015` adds a **nullable** `owner_id` column + a per-table index to the 7 content tables (`files`, `shares`, `memories`, `activity_log`, `webhooks`, `contacts`, `bundle_versions`) — purely additive (`ALTER TABLE ADD` + `CREATE INDEX`, no DROP/rebuild), forward-only, so existing rows and inserts that omit it just get `NULL`. `POST /api/public/v1/admin/backfill-owner` (**owner browser session only** — not bearer-callable, since it is a one-time DB-wide migration op, which also keeps it correctly out of the agent-facing surfaces; idempotent) assigns `owner_id` on every `NULL` row to the resolved deployment owner and reports per-table `{ updated, remainingNull }`; it **fails closed (409)** when the owner can't be resolved, and only ever touches `NULL` rows (never reassigns). The `complete` flag is observational, **not a Phase-2 gate** (inserts still write `NULL` in 1a; Phase 2 populates owner-on-insert then re-runs + verifies). At the current single-owner scale (~1.2k rows) one pass per table is far under D1's statement cap. Insert sites are deliberately left writing `NULL` until Phase 2 populates owner-on-insert + enables filtering (and re-runs the backfill to sweep any interim nulls). Local-only, not deployed; the migration + backfill run at Phase 1's eventual promotion.

- **Multi-tenancy Phase 0 — ownership resolution (#30).** Foundation for per-owner data isolation; **behaviour-neutral** (an owner id is now resolved and threaded through auth, but nothing consumes it for authorization yet — no schema change, no query filtering). `resolveOwnerUserId(db)` maps `OWNER_EMAIL` → `es_system__auth_user.id` and **fails closed on ambiguity**: the auth-user uniqueness is on the *raw* email, so case-only duplicates (`Owner@x`/`owner@x`) can coexist — a case-insensitive match would hit both, so resolution returns null on more than one match rather than binding to an arbitrary one (found in review). The documented null policy for later phases: `OWNER_EMAIL` unset ⇒ legacy trust-any; set-but-unresolved ⇒ Phase 2 must fail closed, never fall through to the whole drive. The global `AGENT_TOKEN` bearer — previously the only principal with `userId: null` — is now bound to the deployment owner in `lib/mcp-auth.ts`, and `RestAuth` carries the resolved `ownerId` (session → `auth.user.id`, bearer → the token's user). Verified the full suite stays green (83 integration + 47 unit); the test harness now creates + seeds the platform `es_system__auth_user` table (`seedOwner`). Later phases add the `owner_id` column (Phase 1) and the query filtering + adversarial isolation suite (Phase 2). Local-only, not deployed.

- **Share download URLs now live 300s (was 90s) and report their own lifetime (#47)** — 90 seconds is hostile to this product's primary user: an agent that fetches `downloadUrl`, thinks, maybe calls another tool, and *then* downloads could blow the window. It failed as a bare `403`, which agents misdiagnose as "geo-blocked" rather than "expired" — one did exactly that.
  - `SHARE_DOWNLOAD_URL_TTL_SECS` 90 → **300**, matching the owner-side `GET /v1/files/:id/preview`, which already used 300s. The two surfaces are doing the same thing and now share one constant in `server/src/types.ts`. The signature is validated when the request *starts*, so a slow transfer of a large file never needed a long TTL — only the issue→start gap does.
  - `GET /s/:shareId/download` now returns **`expiresInSecs`** beside the existing `expiresAt`, matching `preview`'s shape (relative is robust to client clock skew).
  - `preview` hardcoded `300` twice — in the presign call and in the response body — where the two could silently drift. Both now read `PREVIEW_URL_TTL_SECS`. A test asserts the reported lifetime equals the one the URL was actually signed with, for both surfaces.
  - **Trade-off, recorded deliberately:** `downloadCount` increments when the URL is *issued*, not when bytes are fetched, and a presigned URL is unauthenticated — so within its TTL a leaked URL can be re-fetched without counting against `maxDownloads`. This widens that window 3.3×. Audit batch 1 chose 90s for exactly this reason; 300s is judged an acceptable trade given the URL is single-target, unguessable, and still far shorter than the share itself. Counting at fetch time would decouple the two properly (#47).
  - Agent-facing surfaces updated: `guide.ts` now derives the number from the constant (it previously hardcoded "90 seconds" **and** documented the response as `{ downloadUrl, filename, size }`, omitting the `expiresAt` the server was already sending). `skill/references/receiving.md` gained a 403 triage table — XML `<Code>ExpiredRequest</Code>` means re-request a fresh URL, a Cloudflare HTML page means a genuine network block — so a recipient agent stops guessing.

### Fixed

- **Admin control plane fails open when `OWNER_EMAIL` is unset (#30 Part ② Task 4 review, MAJOR)** — `/api/public/v1/admin/*` is exempted from the access-gate (so the owner is never locked out by a stale `user_access` row), which makes `assertAdmin` the *only* guard on those routes. It called `isRequestOwner()`, which trusts any authenticated session when `OWNER_EMAIL` is unset (the correct default for plain drive access, wrong for admin) — so a signup-enabled deploy that hadn't set `OWNER_EMAIL` yet granted approve/reject/allowlist/suspend/backfill to **any** logged-in user. `assertAdmin` now resolves the owner via `resolveOwnerUserId` and requires an exact id match; `OWNER_EMAIL` unset, no match, or a case-only-duplicate ambiguity all resolve to `null`, which denies every caller — fail closed, no trust-any path. TDD: the failing test (non-owner session, `OWNER_EMAIL` unset, → 403 `not_admin`) was written and confirmed red before the fix. One pre-existing test relied on the old trust-any-to-reach-the-handler path (`POST /admin/backfill-owner` expecting its own 409 `owner_unresolved`) — updated to expect the new 403 `not_admin` from `assertAdmin` itself, since that check now runs first.
  - **Defense-in-depth: the owner-id guard now covers all four decision routes, not just `suspend`.** `setDecidedStatus` (shared by approve/reject/suspend/unsuspend) now refuses to act on the resolved owner's id centrally, so `reject` and `unsuspend` get the same `400 cannot_suspend_owner` protection `suspend` already had (previously safe only via the invariant that the owner never gets a `user_access` row). The `suspend` route's own duplicate owner-resolution + check was removed — now redundant, since `assertAdmin`'s fail-closed guarantee means the caller reaching any admin handler already **is** the resolved owner.
  - **`POST /allowlist` now validates the email shape and length** — previously accepted any non-empty string as the allowlist PK. Now requires exactly one `@` with non-empty local/domain parts and caps length at 254 chars (RFC 5321 max), `400 invalid_email` otherwise.
  - **`DELETE /allowlist/:email` no longer 500s on a malformed percent-escape** — a bare `%` in the path segment threw an uncaught `URIError` from `decodeURIComponent`; now caught and returned as `400 invalid_email`.
  - Suite green: 47 unit + 183 integration (7 new / 1 updated).

- **Non-ASCII filenames broke the binding ↔ presigned-URL boundary (#44)** — any name containing non-ASCII characters (Chinese, emoji, accented Latin) failed whenever an operation crossed between the two storage APIs, in both directions: a REST presigned upload 404'd at `/upload/complete` (`upload_not_found`), and — the dangerous one — an MCP-written file was listed, readable via `read_file`, and **silently undownloadable through every download path, including share links handed to a recipient**.
  - **Root cause:** the SDK's `path` argument means two different things. The **binding** family (`put`/`get`/`head`/`delete`) treats it as a **literal key**; the **presign** family embeds it in the URL **verbatim** and S3/R2 URL-decodes it **once** when serving. We handed both the same pre-encoded string, so they operated on two different keys for any name where `encodeURIComponent` is not a no-op. ASCII names are a no-op — which is why it stayed hidden.
  - **Verified empirically against production before choosing a fix:** an already-encoded path came back inside the signed URL as `%E6…`, not `%25E6…`, proving the presign family adds no encoding. This **rules out** the "pass raw everywhere and let the SDK encode" approach (the client would percent-encode on send and break the signature) in favour of this issue's documented fallback.
  - **Fix:** one canonical key — `${fileId}/${rawFilename}` — defined once in `lib/object-keys.ts`. The binding receives it as-is; the presign family receives `presignPath(key)`. Replaces four independent re-derivations of the scheme (`routes/files.ts`, `lib/pending-uploads.ts`, `lib/mcp-tools.ts`, `lib/peering.ts`) and covers the bundle manifest/history writers too. All **read** paths resolve the key from the stored `s3Uri`, and MCP `write_file` now overwrites at the stored key rather than re-deriving one from the current name — so a rename followed by an overwrite no longer strands the old object (the reconciler keys off the still-live file id and would never reap it).
  - **Migration:** none. Verified against the live drive — 0 non-ASCII or awkward (`space`/`%`/`+`/`#`) filenames across all 38 folders — so no stored key changes form. The safety does not rest on ASCII-ness alone: reads re-encode whatever is recorded in `s3Uri`, and that URI records each object's true physical key at write time (encoded under the old code, raw under the new), so any object — old or new — remains resolvable. A stray non-ASCII **orphan** left by earlier probe testing has no row, so it is already invisible to every read path and is reaped by the orphan reconciler (which keys off the id segment, unaffected by name encoding).
  - **Test harness fixed first:** the in-memory storage mock returned a fake presigned URL and modelled no decode semantics, so it could not reproduce this class of bug at all. It now mirrors the real split (verbatim URL + single decode vs. literal key) and exposes `putViaPresignedUrl` / `getViaPresignedUrl` to simulate the client's direct PUT/GET. 17 cases cover both directions, share-link download, and pending-upload cleanup — each with an ASCII twin to lock in that the working path does not regress.

- **MCP endpoint answered `GET`/`DELETE` with `404` instead of `405`** — the Streamable HTTP spec requires the MCP endpoint to support both `POST` and `GET`, and says a server offering no SSE stream **MUST** signal that with `405 Method Not Allowed`. Only `POST /` was routed, so Hono fell through to `404`. That is actively wrong rather than merely untidy: in MCP a `404` means *"this session was terminated — start a new one with a fresh `InitializeRequest`"*, so a Streamable HTTP client probing `GET` could be pushed into a needless re-initialize loop. `GET` and `DELETE` now return `405` with an `Allow: POST` header (`GET` = no SSE stream; `DELETE` = stateless, no client-initiated session termination). Documented in `docs/api/mcp.md`; covered by two transport tests.

### Security

- **Scope enforcement on every REST v1 endpoint (#3)** — `requireDualAuth` now resolves the bearer auth context once, enforces a capability scope derived from method + route (`GET/HEAD` → `read:drive`, `/v1/shares*` mutations → `share:create`, all other mutations → `write:drive`), and stores the context in Hono `c.var` for route-level checks. ### Changed

- **Trash no longer hard-purges on path reuse (#4)** — soft-deleting now renames the subtree root into a tombstone namespace (`<path>~trash~<rootId>`, descendants prefix-rewritten), so creating a file/folder at a previously-trashed path no longer silently destroys the trashed copy. Restore strips the tombstone suffix, returns `409 path_conflict` if the original path is occupied by a live item, and rows trashed before this scheme restore unchanged (legacy same-path purge kept only as fallback for those rows). `GET /files/trash` returns display paths with markers stripped.

### Fixed

- **Webhook delivery validates the destination once per attempt (#5)** — `deliverWebhook` performed the DoH SSRF validation, then `postWebhook` validated again, and the 5xx retry validated a third time (4–6 DNS queries per delivery). ### Added

- **Trash / recycle bin (YRZ-128)** — DELETE on a file or folder is now a soft-delete: row stays in `files` with `deleted_at` set, R2 object stays put, and the row is hidden from every read path (REST list/search/get/preview, batch delete/move, MCP `list_files`/`read_file`/`write_file`/`search_files`/`create_share`, public-share download). ### Fixed

- **T3.1 audit MEDIUM follow-ups (CLI OAuth)** — three issues from the post-T3.1 review now addressed:
  - **Atomic token refresh** (`cli/src/lib/mcp-client.ts`): `refreshIfNeeded` now builds a `next` config object, persists it to disk first, and only then mutates the in-memory options. Previously the in-memory object was updated before the disk write, so a write failure left the caller using a token that was never persisted.
  - **Preserve refresh error context** (`cli/src/lib/mcp-client.ts`): the catch block previously discarded the underlying refresh error and threw a generic "Session expired" message. Now includes the original error message so network failures, invalid_grant responses, etc. are debuggable without raising logging.
  - **Client-side scope whitelist** (`cli/src/lib/oauth.ts`): `--scope` is now validated against the known scope set (`read:drive`, `write:drive`, `share:create`, `read:memory`, `write:memory`, `read:skills`, `write:skills`) before being sent. Unknown scope tokens are rejected with a clear "Known scopes: ..." message instead of being passed to the server. Also deduplicates and collapses whitespace.
- **OAuth bearer tokens now work on `/api/public/v1/*`** — `requireDualAuth` middleware previously accepted only EdgeSpark session or `AGENT_TOKEN`, silently rejecting OAuth bearer tokens that the same deployment hands out via `/api/public/oauth/token`. The middleware now delegates to `authenticateMcpBearer`, so any path the CLI exercises (`sync push` → `/v1/bundles/commit`, `/v1/files/...` orphan deletion, etc.) accepts OAuth tokens with the same scope checks the MCP surface uses. Pre-existing bug that surfaced during T4.2 smoke testing.
- **`sync push` no longer wipes `.history/*` snapshots** — `deleteOrphans()` walked the cloud bundle and considered any file not in the local manifest as orphan, which deleted server-managed `${prefix}/.history/<versionId>.json` snapshots on every push (eating the version history). Orphan detection now excludes `${prefix}/.history/`.
- **`sync rollback` prints local-state hint** — rollback creates a new versionId on the server but local sync-state files on other machines still point at the prior version. The rollback output now reminds users to re-anchor with `sync pull`.

### Security

- **Rate limiter TOCTOU race fixed** — share password attempts now use atomic SQL increment (`count = count + 1`) instead of read-modify-write, preventing concurrent bypass of the 5/15min limit.
- **Webhook SSRF hardened** — webhook URLs are now restricted to HTTPS with a public DNS hostname. **All IP literals are rejected**: every IPv4 dotted-quad (private, loopback, link-local, *and public*) and every IPv6 literal (including `[::1]`, `[fe80::]`, `[::ffff:169.254.169.254]`, ULA `fd00::`). `localhost`, `*.localhost`, and `*.internal` are also rejected. Rationale: forcing DNS resolution closes off direct-IP SSRF vectors and future RFC additions; if you previously used a raw IPv4 webhook URL, switch to a hostname.
- **Share access tokens are now revocable** — `shares` table gained a `password_version` column; tokens are bound to the version at issue time so rotating a share's password invalidates outstanding tokens.
- **Filename encoding for upload presigned URLs** — filenames containing `%` (and other URL-reserved characters) no longer fail PUT 400; the R2 object key path is properly encoded.
- **Webhook secret hint added** — `POST /api/public/v1/webhooks` response now includes a `hint` reminding clients the secret is shown only once.
- **Share metadata leak reduced** — exhausted/expired shares return minimal information to unauthenticated callers.

### Added

Rollback uses the current versionId as `ifMatch` so concurrent commits during rollback get a clean conflict error. `--yes` / `--force` skip the interactive confirmation.
- **Bundle versioning (Phase 3, CLI)** — `adrive sync push` switched from destructive `write_file(manifest.json)` to the new `/bundles/commit` endpoint with If-Match. ### Changed

- **ZIP download memory limit lowered** from 50MB to 30MB to keep peak memory well below the Workers 128MB cap.
- **Folder rename and delete are now atomic** via `db.batch()` — eliminates partial-failure inconsistency where some descendant paths were updated and others not.
