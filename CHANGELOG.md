## [Unreleased]

### Fixed

- **The guide's `restApi` summary line omitted three mounted REST areas.** `agentSurfaces.restApi` listed files, folders, shares, memory, bundles, webhooks, and activity — but not `spaces`, `tokens`, or `contacts`, all mounted in `server/src/index.ts`. Same failure mode as the `agentSurfaces.mcp` line fixed earlier: an agent reading the summary to learn which REST areas exist would never discover them. The line now names all ten and states explicitly that `/account/*` is covered by the `accountAccess` section and `/admin/*` is owner tooling deliberately kept off the agent surfaces (the guide already said so in its own `note` field). `llms.txt` was already complete.
- **The drift guard now covers REST mounts, not just MCP tools.** `agent-surfaces.test.ts` extracts every `/api/public/v1/*` mount from `index.ts` and requires each to appear in the guide's `restApi` line. Omissions must be declared in a `restAreasDocumentedElsewhere` map with a stated reason, so hiding a surface from agents becomes a deliberate, reviewable act rather than an oversight. RED-verified in both directions: regressing the summary line named exactly `tokens`, `contacts`, `spaces`; mounting a new `/v1/reports` route without documenting it named `reports`.

- **[SECURITY-RELEVANT DOC] Five surfaces stated the exact opposite of how the access gate treats bearer tokens.** `skill/references/access.md`, `docs/api/access.md`, `docs/api/README.md`, `skill/references/api-reference.md`, and — served live in production — the `accountAccess` section of `GET /api/public/guide` all claimed *"bearer/agent tokens are never gated"*. In fact `requireActiveAccess` (`server/src/middleware/access-gate.ts:39-79`) checks **every user-bound bearer** (OAuth tokens and minted drive tokens) against its principal's `user_access.status`, on REST and MCP alike; the middleware's own comment says *"Bearers are gated too, not just sessions."* Only the legacy install-wide `AGENT_TOKEN` on an `OWNER_EMAIL`-unset deployment skips the check, having no principal to gate. The code is stricter than the docs claimed, so nothing was exposed — but an agent trusting the docs would believe its OAuth token survives the owner suspending the account, and would treat the resulting `403 access_suspended` as a transient error worth retrying. All five now state that bearers are gated, that suspension kills existing tokens immediately, and that these 403s must not be retried.
- **Docs described the drive as single-user long after it stopped being one.** `README.md` (both the English Key Features and the Chinese 核心能力) never mentioned Shared Spaces, multi-owner isolation, or public self-signup — the three largest shipped features — and `docs/api/README.md` still said *"Sign-up stays disabled … until go-live"* while `configs/auth-config.yaml` has carried `disableSignUp: false` since go-live. The README endpoint tables were also missing all 9 `/admin/*` routes, 3 of the 11 `/spaces/*` routes (`GET /:id`, `GET /:id/members`, `PATCH /:id/members/:userId`), the `cli/` directory, and 5 of the 12 web pages.
- **Two code comments outlived the code they described.** `server/src/lib/owner.ts` still asserted *"content tables carry no per-owner column (true multi-tenancy is a separate project)"* — contradicted by the `ownerId` columns #30 shipped — and `configs/auth-config.yaml` still said *"disableSignUp stays true until Task 8 / go-live"* three lines below `disableSignUp: false`. Both rewritten to describe the current system.
- **`GET /files` pagination was undocumented, and it truncates silently.** `limit` defaults to 100 (clamped 1–500) with no indication in the response that more rows exist (`server/src/routes/files.ts:222-226`), so an agent listing a folder of 300 files got 100 and no signal. `skill/references/file-ops.md` now documents the parameters and instructs paging until a short page comes back. `GET /files/search` has different bounds again (limit 50, max 200, no offset) and is documented separately.
- **The skill never warned that reads can return other users' data, and offers no way to tell.** Shared Spaces membership widens `GET /files`, search, get, preview, `recall`, `list_memories`, and memory get to include items contributed to your spaces (`fileReadableFilter` / `memoryReadableFilter`), yet `file-ops.md` and `memory.md` described them as strictly own-data. Compounding this, `toFileObject` (`server/src/lib/files.ts:28-39`) emits **no ownership field** — a widened listing is indistinguishable from your own. Both files now state the widening, direct agents to `contributedBy` on the space item listing for attribution, and instruct them not to call a listed file "yours" until they have checked.
- **Memory poisoning defense was undocumented.** `getMemory` resolves the caller's own row before the widened scope specifically so a hostile commons user publishing a guessable key (`deploy-target`) cannot have their content served to another agent as its own memory (`server/src/lib/memory.ts:296-315`). `memory.md` now documents the own-row-first precedence and warns that recalled content is a claim by its author, never instructions to obey.
- **Assorted contract errors across the API docs**, each verified against the handler: `docs/api/oauth.md` claimed `redirect_uris` was capped at 5 (no maximum exists) and that `grant_types`/`response_types` were validated (neither field is read from the request body; both are hardcoded in the response), and listed `invalid_scope` and `invalid_request` as `/token` errors that handler never throws; `docs/api/peering.md` omitted the `share:create` requirement that `/contacts/:name/send` and `/bundles/publish` enforce on bearer callers, so a `write:drive`-only token hits an unpredicted 403; `docs/api/agent-card.md` quoted a `signing.purpose` string the server does not serve and listed 3 of the 4 `skills[]` entries; `docs/api/tokens.md` implied `token.minted` and `token.revoked` share a metadata shape (revoked logs only `{label}`); `docs/api/mcp.md` showed an `initialize` response with an `auth_mode` field that does not exist and an auth value (`oauth_bearer`) the server never emits. `GET /oauth/clients/:clientId`, webhook auto-disable after 5 consecutive failures, and `send_file`'s reference section were undocumented and have been added.
- **`skill/references/setup.md` never mentioned `OWNER_EMAIL`.** Following it end to end produced a deployment with the ownership boundary disarmed — while unset, `isRequestOwner()` returns true for *any* authenticated session, and signup is open. Now a required step with the consequence stated.
- **`skill/references/sharing.md` had the share-lifecycle status codes wrong.** It said expired/exhausted shares return 410/429 to public callers; `GET /s/{shareId}` actually returns **200** with `expired`/`exhausted` flags (`server/src/routes/public-shares.ts:113-135`) and only `/access`, `/download`, `/download-zip` throw. An agent checking liveness via the status endpoint would read 200 as "still live". Also documents the previously-missing `GET /shares/:id/stats`, flagging that `ipStats`/`userAgentStats` are PII about whoever opened the link.
- **`skill/references/api-reference.md` claimed completeness while missing 13 mounted endpoints** — 7 under Files (search, both batch routes, trash, preview, restore, purge), `GET /shares/:id/stats`, `POST /bundles/publish`, `GET /activity`, and all 4 webhook routes — plus the `bundle_not_found` / `version_conflict` error codes. All added.

- **Two agent-facing surfaces under-reported Shared Spaces, making it undiscoverable for agents that read only the summary.** The Spaces feature shipped with `llms.txt` and the installable skill fully updated, but two enumerating surfaces were missed. `GET /api/public/guide`'s `agentSurfaces.mcp` line listed 10 of the 16 registered MCP tools, omitting all six space tools (`list_spaces`, `read_space`, `add_to_space`, `remove_from_space`, `create_space`, `manage_space_members`) — an agent that reads the summary line to learn the tool set would never discover them, even though the same document described the spaces model in full further down. The A2A Agent Card at `/.well-known/agent.json` advertised only `file-exchange`, `memory`, and `bundles`; a `spaces` skill entry was added. No behavior change — every tool was already registered and reachable.
- **Surface drift is now caught mechanically instead of by review.** New `server/src/lib/agent-surfaces.test.ts` (in `npm run test:unit`) diffs the tool set registered in `mcp-tools.ts` against every surface that claims to enumerate it — the guide's `agentSurfaces.mcp` line, `llms.txt`'s `Tools:` block, and `skill/references/mcp.md` — so adding a tool without updating a surface fails the suite. Each check is narrowed to the specific passage making the claim rather than searching the whole file: the first version of this test searched file-wide and **passed a deliberately reverted `guide.ts`**, because the stale summary line sat in a file whose spaces section mentioned the missing tools further down. All three checks were RED-verified by breaking each surface in turn. `CLAUDE.md` records both the Agent Card as a seventh mandatory surface and the two lessons.

- **[MAJOR] Four more live cross-owner bugs of the #65 shape, found by auditing every `files.path`-keyed lookup after the #65 fix.** Same root cause as #65 throughout: a lookup keyed on `files.path` with **no owner filter**, in code that then overwrites, serves, or destroys. Paths became per-owner unique in #30, so two owners can hold the same path and an unscoped lookup silently resolves the wrong owner's row. Every fix uses the established pattern (`ownerId ? eq(files.ownerId, ownerId) : undefined` folded into the `and(...)`), so a legacy null-owner deployment keeps prior behavior.
  - **[CRITICAL] A bundle push could overwrite another owner's manifest row and clobber their R2 object.** `routes/bundles.ts` resolved `<prefix>/manifest.json` by path alone at three sites; the commit handler's lookup drives both the R2 object key (`driveObjectKey(manifestFileId, …)`) and a `db.update(files).where(eq(files.id, existingManifestRow.id))`. `bundle_versions` is unique on `(ownerId, prefix)`, so owner A pushing to `/bundles/app` is entirely legal even when owner B already holds a live bundle there — and the unscoped lookup resolved **B's** row, PUT A's manifest bytes over B's R2 object, and rewrote B's DB row with A's size/hash/`s3Uri` while leaving `ownerId = B`. B's bundle was destroyed, in place, with no error. All three lookups (the history-snapshot pair in `snapshotCurrentManifestToHistory` and the commit handler's `existingManifestRow`) are now owner-scoped.
  - **[CRITICAL] Cross-owner disclosure through the history snapshot.** The same unscoped `manifest.json` lookup fed `snapshotCurrentManifestToHistory`, so A's push could copy **B's** manifest bytes — full file list, per-file hashes, `machineId` — into `<prefix>/.history/<versionId>.json` inside A's own drive, where A can read it via `GET /v1/bundles/history` and `/v1/bundles/manifest`. Closed by the same owner filter.
  - **[HIGH] The PUBLIC bundle endpoint could serve another owner's private files.** `routes/public-bundles.ts` resolved both `manifest.json` and every manifest-listed file by path alone, on an **unauthenticated** route. With A publishing `/bundles/app` and B holding unpublished rows at the same paths, the endpoint could serve B's manifest as A's and hand out **presigned download URLs for B's private file bytes** to anyone with the public id. `bundle.ownerId` was already available on the `bundleVersions` row; it is now threaded into every file resolution in the route (`/current`, `/manifest`, `/file`). The manifest-listed-paths allowlist and the `.history` exclusion are unchanged.
  - **[HIGH] The stale-trash sweep could destroy other owners' LIVE files.** `hardPurgeSubtree`'s subtree delete had **no `deletedAt` filter**, and `maybePurgeStaleTrash` passes `row.ownerId ?? null` — which is `null` for a legacy pre-#30 trashed row, leaving the sweep fully unscoped. A legacy null-owner trashed `/notes` aging past the 30-day retention would run `DELETE … WHERE path LIKE '/notes/%'` with no owner and no `deletedAt` predicate, destroying owners A's and B's **live** `/notes/*` rows and their R2 bytes. Fixed in depth, both layers: (a) the subtree delete now matches the root by `files.id` and requires `isNotNull(files.deletedAt)` on every descendant, so a purge can never take a live row regardless of scoping — the same floor is applied to the row set whose R2 objects get deleted; (b) `maybePurgeStaleTrash` now skips a null-owner root outright when any owned row shares its path prefix, rather than sweeping unscoped across owners. Same-owner purging and legacy single-owner deployments are unchanged.
  - **[LOW] Cosmetic cross-owner name leak.** `lib/shares.ts` and `routes/shares.ts` resolved a share's folder by path with no owner filter, only to derive the display `targetName` — another owner's folder name could surface on your share. Both scoped to `share.ownerId`.
  - Regression coverage in a new two-owner adversarial suite (`cross-owner-path-lookups.integration.test.ts`, 12 tests): A's push leaves B's manifest row, `s3Uri`, size and R2 bytes byte-identical while A gets their own manifest; A's `.history` snapshot contains neither B's `machineId` nor B's file list; the public endpoint serves A's manifest and **404s** on a path only B holds; `hardPurgeSubtree` leaves a live sibling row and its bytes intact; and the stale sweep skips the cross-owner null-owner root. Same-owner behavior is asserted in every case (A's own manifest IS updated in place, A's own trashed subtree IS fully purged, A's own bundle file IS still downloadable, owner-scoped and legacy single-owner sweeps still purge). **RED-verified** by temporarily reverting each filter: both CRITICALs, the public-disclosure path, and both purge layers each produced failing tests against the pre-fix code. Suite green: 47 unit + 358 → 370 integration, server typecheck clean. No schema change, so no migration; not yet deployed.

- **[MAJOR] One owner's ordinary write could hard-purge another owner's trashed file — bytes and all (#65).** `purgeConflictingTrashAtPath` (`lib/trash.ts`) looked a row up by `path` with **no owner filter**, then hard-purged it (DB row + R2 object). The helper predates #30: when `files.path` was globally unique, "the trashed row at this path" was unambiguously the caller's. #30's `(owner_id, path)` composite made that assumption false, and this call site was missed in the owner-scoping sweep — so owner A creating or uploading `/notes/x.md` in **A's own drive** silently destroyed owner B's soft-deleted `/notes/x.md`, unrecoverably, with no error and no distinguishing audit trail. The bug was live in production; impact was bounded only because the drive is effectively single-owner today, but signup is open.
  - The lookup is now owner-scoped with the standard #30 pattern (`ownerId ? eq(files.ownerId, ownerId) : undefined`, so a legacy null-owner deployment keeps prior behavior), and the caller's owner is threaded through **all seven call sites**: `write_file` (`lib/mcp-tools.ts`), folder create (`routes/folders.ts`), upload init / batch move / rename-move (`routes/files.ts`), and the bundle history + manifest paths (`routes/bundles.ts`, via a new `ownerId` parameter on `snapshotCurrentManifestToHistory` bound to the same owner as the surrounding bundle write). Same-owner behavior is unchanged — the caller's own conflicting trash is still purged, which is the feature.
  - **Two more instances of the same bug shape, found while auditing `lib/trash.ts` and fixed with it.** `hardPurgeSubtree` expanded the subtree and ran its `path LIKE '<root>/%'` deletes (files and shares) **unscoped**, so purging a legacy-trashed folder swept another owner's rows under the same path; and `restoreSubtree` expanded unscoped the same way, so restoring a legacy-trashed folder silently un-trashed and path-rewrote another owner's trashed descendants. Both now take and apply the caller's owner. Audited the rest of the module: `maybePurgeStaleTrash` and the non-folder branches key off `files.id` (a globally unique PK) and needed no change.
  - Regression coverage in `ownership-collision` (two-owner adversarial suite): A's upload, folder create, MCP `write_file`, and folder restore each leave B's trashed row **and its R2 object** intact and restorable — plus an assertion that A's *own* trashed file at that path is still purged. All four cross-owner tests confirmed **RED** against the pre-fix code; the same-owner test passes on both sides. Suite green: 47 unit + 353 → 358 integration (5 new tests), server typecheck clean. No schema change, so no migration; not yet deployed.

- **Shared Spaces P2 — whole-branch review fixes on the public commons.** One IMPORTANT + three minors from the branch review of P2 Tasks 1–4.
  - **[IMPORTANT] A key/path collision served a FOREIGN row for your own key — a memory-poisoning vector.** `getMemory`'s key branch (`lib/memory.ts`) and `read_file`'s path lookup (`lib/mcp-tools.ts`) queried with the WIDENED readable scope and `.limit(1)`, with no tie-break toward the caller's own row. Keys and paths are unique per owner but never globally, so in P1 a collision required a mutually-consented invite space — **the public commons broke that assumption**, making every active user collide with every other. A hostile user publishing a commons memory under a guessable key (`deploy-target`) could have their content returned to another agent **as its own memory**, which the agent would then act on. Integrity/poisoning, not confidentiality. Both reads are now **own-row-first**: the caller's own row wins, and the widened scope is a fallback only for refs they don't own — the precedence `write_file` already enforced. The `id` branch needed no change (`memories.id` is a globally unique PK), and own-row-first is skipped entirely on write paths where the scope already IS the strict owner filter. Audited every other widened read: the rest are list/search (no `.limit(1)` tie-break) or by `files.id` (unique PK), so no other site was affected. The stale comment claiming the collision was "acceptable in P1" is gone.
    - Confirmed with a probe that the pre-fix behavior is genuinely **query-plan-dependent**: on a pristine test DB SQLite picks a `MULTI-INDEX OR` that happens to probe the owner branch first and masks the bug, but once optimizer statistics exist (`ANALYZE`) the plan degrades to a `SCAN`/skip-scan and returns the **attacker's** row. The new regression tests pin that adversarial-but-legal plan so they actually exercise the collision instead of trusting the planner — verified RED against the pre-fix code.
  - **[Minor] `Clear commons` now requires a type-to-confirm.** `SpaceViewPage` used the same `window.confirm` for the commons as for an invite space's "Delete space", but on the commons it wipes EVERY user's contributed references instance-wide. The public space now opens an inline type-`CLEAR` panel (plain Tailwind-slate, no new deps) stating the instance-wide blast radius and that underlying files/memory survive; invite-space delete keeps the plain confirm.
  - **[Minor] Defensive orphan cleanup on commons re-bootstrap.** `space_items` has no FK to `spaces` and `PUBLIC_COMMONS_ID` is a fixed constant, so an item inserted in the TOCTOU window just before a `Clear commons` could survive and become live in the "fresh" commons. `ensurePublicCommons` now sweeps `space_items` for the commons id when — and only when — its own insert actually created the row (gated on `returning()`, so a bootstrap that lost the `onConflictDoNothing` race can't wipe the winner's items).
  - **[Minor] Documented the `OWNER_EMAIL`-rotation trap.** `spaces.creatorId` is stamped once at bootstrap and never re-bound, so rotating `OWNER_EMAIL` leaves commons moderation with the OLD account while the new owner silently becomes an ordinary contributor. Noted under "The public commons" in `docs/api/spaces.md` (with both hand-over routes: clear-and-re-bootstrap, or an explicit `editor` row) and in the skill's `references/spaces.md`; manifest regenerated.
  - **Test coverage for the commons deletion path**, previously zero: a non-creator's `DELETE /v1/spaces/<commonsId>` → 403 with items intact; the creator clearing it removes every `space_item` while the underlying files/memory survive and the cross-owner read is revoked; and the next spaces request re-bootstraps an empty commons under the same fixed id, sweeping a planted orphan item.
  - Suite green: 47 unit + 345 integration → 47 unit + 353 integration (8 new tests). The collision and orphan-sweep fixes were each confirmed RED against the pre-fix code. `ownership-isolation`/`ownership-collision` and all `spaces-*` suites re-run green; server + web typecheck and web build clean. Local-only, nothing deployed.

- **Shared Spaces P2 — adversarial-review fixes on the public commons.** Six findings from the review of P2 Tasks 1–2, one of them empirically confirmed by a probe.
  - **[HIGH] The owner could byte-overwrite any contributor's private file.** `canEditFileViaSpace` built its editor set from `spaces WHERE creatorId = me` ∪ `space_members WHERE role='editor'`. The commons' `creatorId` is the deployment owner, so EVERY file any user contributed to the commons became owner-writable in place through the `write_file` editor relaxation — the probe overwrote another user's file at their own S3 key with their `ownerId` unchanged. Publishing to the commons is consent to be **read**, never consent to have your bytes replaced. Both branches now exclude `visibility='public'` spaces (`ne(spaces.visibility, "public")`, plus a join on the `space_members` branch so an owner-granted `editor` row on the commons cannot resurrect the grant). Live-reference byte editing is now an INVITE-space power only; commons moderation removes the **reference row**, never the resource.
  - **The active check now gates the commons uniformly.** `userSpaceIds` added the commons unconditionally when an explicit `space_members` row existed, running `isActiveUser` only on the no-row branch — so a suspended user holding a commons row got the commons (and a non-empty `accessibleFileIds`) while `resolveSpaceRole` correctly returned null, falsifying the "role is never null for an id from `userSpaceIds`" assumption its callers rely on. The check is hoisted so it applies regardless of a stored row (the commons *creator* is exempt — `resolveSpaceRole` derives `creator` from `spaces.creatorId` before any status check). Not live-exploitable (the #30 gate denies suspended requests first); it would have become a leak the moment a read path landed outside that gate.
  - **The owner can now demote a commons user.** The role resolver ratcheted a stored role UP only, so an owner-set `viewer` row on the commons still resolved `contributor` and the only remedy for commons spam was globally suspending the account. A stored row on the commons is now authoritative in **both** directions (`viewer` → read-only, `editor` → item moderation only, no row → the implicit `contributor` floor); the creator still resolves `creator`.
  - **The commons member roster is creator-only.** `GET /spaces/:id/members` asserted `viewer`, which every active user clears on the commons via implicit membership — handing the handler's `esSystemAuthUser.email` join, including the deployment owner's login email, to every user of the drive. Public spaces now return `403 space_forbidden` to non-creators; invite spaces keep the P1 viewer+ behavior. Item attribution still reaches everyone through `contributedBy`.
  - **`memberCount` no longer understates the commons audience.** `spaceCounts` returned `space_members count + 1`, and the commons materializes no rows — so the one space everyone can read reported `1`, the smallest number in the list, at exactly the publish decision point. It is now `null` for public spaces ("everyone on this drive", rendered as such by the web and documented in `docs/api/spaces.md`); invite spaces are unchanged.
  - **Indexed the hot commons lookup.** `findPublicCommonsId` (`WHERE visibility = 'public' LIMIT 1`) runs on every `fileReadableFilter`/`memoryReadableFilter` call — every list/get/search/preview/recall — against an unindexed column. Added `idx_spaces_visibility`, migration `drizzle/0021_spaces_visibility_index.sql` (additive `CREATE INDEX` only, no PRAGMA). **Not applied or deployed.**
  - Suite green: 47 unit + 345 integration (8 new regression tests; the fixes for the first three findings were each confirmed RED against the pre-fix code). `ownership-isolation`/`ownership-collision` and all `spaces-*` suites re-run green. Local-only, nothing deployed.

- **Non-ASCII filenames broke the binding ↔ presigned-URL boundary (#44)** — any name containing non-ASCII characters (Chinese, emoji, accented Latin) failed whenever an operation crossed between the two storage APIs, in both directions: a REST presigned upload 404'd at `/upload/complete` (`upload_not_found`), and — the dangerous one — an MCP-written file was listed, readable via `read_file`, and **silently undownloadable through every download path, including share links handed to a recipient**.
  - **Root cause:** the SDK's `path` argument means two different things. The **binding** family (`put`/`get`/`head`/`delete`) treats it as a **literal key**; the **presign** family embeds it in the URL **verbatim** and S3/R2 URL-decodes it **once** when serving. We handed both the same pre-encoded string, so they operated on two different keys for any name where `encodeURIComponent` is not a no-op. ASCII names are a no-op — which is why it stayed hidden.
  - **Verified empirically against production before choosing a fix:** an already-encoded path came back inside the signed URL as `%E6…`, not `%25E6…`, proving the presign family adds no encoding. This **rules out** the "pass raw everywhere and let the SDK encode" approach (the client would percent-encode on send and break the signature) in favour of this issue's documented fallback.
  - **Fix:** one canonical key — `${fileId}/${rawFilename}` — defined once in `lib/object-keys.ts`. The binding receives it as-is; the presign family receives `presignPath(key)`. Replaces four independent re-derivations of the scheme (`routes/files.ts`, `lib/pending-uploads.ts`, `lib/mcp-tools.ts`, `lib/peering.ts`) and covers the bundle manifest/history writers too. All **read** paths resolve the key from the stored `s3Uri`, and MCP `write_file` now overwrites at the stored key rather than re-deriving one from the current name — so a rename followed by an overwrite no longer strands the old object (the reconciler keys off the still-live file id and would never reap it).

The safety does not rest on ASCII-ness alone: reads re-encode whatever is recorded in `s3Uri`, and that URI records each object's true physical key at write time (encoded under the old code, raw under the new), so any object — old or new — remains resolvable. A stray non-ASCII **orphan** left by earlier probe testing has no row, so it is already invisible to every read path and is reaped by the orphan reconciler (which keys off the id segment, unaffected by name encoding).

### Security

- **Scope enforcement on every REST v1 endpoint (#3)** — `requireDualAuth` now resolves the bearer auth context once, enforces a capability scope derived from method + route (`GET/HEAD` → `read:drive`, `/v1/shares*` mutations → `share:create`, all other mutations → `write:drive`), and stores the context in Hono `c.var` for route-level checks. Routes enforce `path:` scopes wherever the target path is resolvable: file get/preview/upload/complete/move/rename/delete/restore/purge, batch delete/move (per-id `invalid_scope` failures), folder create, bundle commit/current/history/manifest, share create/get/stats/delete, and list endpoints (`/files`, `/files/search`, `/files/trash`, `/shares`, `/activity`) filter rows to the granted prefixes. Webhook management requires unrestricted (`path:/`) access since deliveries span the whole drive. Session (web) auth is unchanged. The ad-hoc `requireBearerFileAccess` / `requireBearerBundleAccess` helpers are replaced by shared `server/src/lib/rest-scopes.ts`.

### Changed

- **Trash no longer hard-purges on path reuse (#4)** — soft-deleting now renames the subtree root into a tombstone namespace (`<path>~trash~<rootId>`, descendants prefix-rewritten), so creating a file/folder at a previously-trashed path no longer silently destroys the trashed copy. Restore strips the tombstone suffix, returns `409 path_conflict` if the original path is occupied by a live item, and rows trashed before this scheme restore unchanged (legacy same-path purge kept only as fallback for those rows). `GET /files/trash` returns display paths with markers stripped.

### Fixed

- **Webhook delivery validates the destination once per attempt (#5)** — `deliverWebhook` performed the DoH SSRF validation, then `postWebhook` validated again, and the 5xx retry validated a third time (4–6 DNS queries per delivery). Validation now runs exactly once per delivery in `deliverWebhook`.

### Added

- **Trash / recycle bin (YRZ-128)** — DELETE on a file or folder is now a soft-delete: row stays in `files` with `deleted_at` set, R2 object stays put, and the row is hidden from every read path (REST list/search/get/preview, batch delete/move, MCP `list_files`/`read_file`/`write_file`/`search_files`/`create_share`, public-share download). ### Fixed

- **T3.1 audit MEDIUM follow-ups (CLI OAuth)** — three issues from the post-T3.1 review now addressed:
  - **Atomic token refresh** (`cli/src/lib/mcp-client.ts`): `refreshIfNeeded` now builds a `next` config object, persists it to disk first, and only then mutates the in-memory options. Previously the in-memory object was updated before the disk write, so a write failure left the caller using a token that was never persisted.
  - **Preserve refresh error context** (`cli/src/lib/mcp-client.ts`): the catch block previously discarded the underlying refresh error and threw a generic "Session expired" message. Now includes the original error message so network failures, invalid_grant responses, etc. are debuggable without raising logging.
  - **Client-side scope whitelist** (`cli/src/lib/oauth.ts`): `--scope` is now validated against the known scope set (`read:drive`, `write:drive`, `share:create`, `read:memory`, `write:memory`, `read:skills`, `write:skills`) before being sent. Unknown scope tokens are rejected with a clear "Known scopes: ..." message instead of being passed to the server. Also deduplicates and collapses whitespace.
- **OAuth bearer tokens now work on `/api/public/v1/*`** — `requireDualAuth` middleware previously accepted only EdgeSpark session or `AGENT_TOKEN`, silently rejecting OAuth bearer tokens that the same deployment hands out via `/api/public/oauth/token`. The middleware now delegates to `authenticateMcpBearer`, so any path the CLI exercises (`sync push` → `/v1/bundles/commit`, `/v1/files/...` orphan deletion, etc.) accepts OAuth tokens with the same scope checks the MCP surface uses. Pre-existing bug that surfaced during T4.2 smoke testing.
- **`sync push` no longer wipes `.history/*` snapshots** — `deleteOrphans()` walked the cloud bundle and considered any file not in the local manifest as orphan, which deleted server-managed `${prefix}/.history/<versionId>.json` snapshots on every push (eating the version history). Orphan detection now excludes `${prefix}/.history/`.
- **`sync rollback` prints local-state hint** — rollback creates a new versionId on the server but local sync-state files on other machines still point at the prior version. The rollback output now reminds users to re-anchor with `sync pull`.

### Security

- **Rate limiter TOCTOU race fixed** — share password attempts now use atomic SQL increment (`count = count + 1`) instead of read-modify-write, preventing concurrent bypass of the 5/15min limit.
- **Webhook SSRF hardened** — webhook URLs are now restricted to HTTPS with a public DNS hostname. **All IP literals are rejected**: every IPv4 dotted-quad (private, loopback, link-local, *and public*) and every IPv6 literal (including `[::1]`, `[fe80::]`, `[::ffff:169.254.169.254]`, ULA `fd00::`). `localhost`, `*.localhost`, and `*.internal` are also rejected. Rationale: forcing DNS resolution closes off direct-IP SSRF vectors and future RFC additions; if you previously used a raw IPv4 webhook URL, switch to a hostname.
- **Share access tokens are now revocable** — `shares` table gained a `password_version` column; tokens are bound to the version at issue time so rotating a share's password invalidates outstanding tokens.
- **Filename encoding for upload presigned URLs** — filenames containing `%` (and other URL-reserved characters) no longer fail PUT 400; the R2 object key path is properly encoded.
- **Webhook secret hint added** — `POST /api/public/v1/webhooks` response now includes a `hint` reminding clients the secret is shown only once.
- **Share metadata leak reduced** — exhausted/expired shares return minimal information to unauthenticated callers.

### Added

Rollback uses the current versionId as `ifMatch` so concurrent commits during rollback get a clean conflict error. `--yes` / `--force` skip the interactive confirmation.
- **Bundle versioning (Phase 3, CLI)** — `adrive sync push` switched from destructive `write_file(manifest.json)` to the new `/bundles/commit` endpoint with If-Match. On 412, push prints a two-option resolution (pull-then-retry, or push --force). `adrive sync pull` now records the cloud's currentVersionId into sync-state after a successful pull, so the next push has a fresh ETag anchor.

### Changed

- **ZIP download memory limit lowered** from 50MB to 30MB to keep peak memory well below the Workers 128MB cap.
- **Folder rename and delete are now atomic** via `db.batch()` — eliminates partial-failure inconsistency where some descendant paths were updated and others not.
